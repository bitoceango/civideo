# 需求文档：R2 存储容量监控 + 已看完视频自动清理（GC）

> 编号：006 ｜ 状态：草稿（待评审）
> 创建日期：2026-06-14 ｜ 关联：`docs/architecture.md`、`cli/`(cpv)、`worker/`

## 1. 背景与目标
R2 按存储量计费，总用量超过约 **500GB** 后成本明显上升。视频体积大、会持续累积。

目标：把 R2 总用量**自动控制在 ~500GB 以内** —— 监控用量；超阈值时**自动删除「已看完且冷却期已过」的旧视频**（按上传时间从旧到新），删到低水位为止；**收藏（我喜欢的）视频永不删**。

**核心目标**：存储成本自动可控、无需人工盯，且不误删孩子还想看的内容。

## 2. 范围
- **本次要做（In scope）**：
  - CLI 算 R2 用量 + 阈值监控（`cpv storage`）。
  - Worker 受保护接口：查询每个视频的「看完状态 + 最后观看时间」。
  - CLI 自动清理（`cpv gc`）：超阈值 → 按策略删到低水位。
  - 配置：容量上限 / 低水位 / 冷却天数 / admin 凭证。
  - 安全：收藏保护、`--dry-run`、删除日志、幂等。
- **本次不做（Out of scope）**：
  - **听书（audiobooks）不纳入自动删除**（音频体积极小，仅计入用量统计）。
  - App UI 的容量显示（可选 P2）。**注：本功能是 CLI/Worker 运维类，「三端同时实现」规则不适用。**
  - 自动转码/降码率省空间（另议）。

## 3. 设计原则 / 约束
- **破坏性操作要稳**：只删「看完 且 ≥冷却天数 无人再看」的视频；**收藏永不删**；删前可 `--dry-run` 预览；删除全程有日志。
- **全自动**（用户选定）：超阈值自动删到低水位（适合放定时任务/CI），但保留 `--dry-run` 与显式开关。
- **复用现有架构、无需新埋点**：用量用 S3 `ListObjectsV2` 累加；「看完」用 Worker 的 D1 `watch_progress`（app→Worker 的进度上报已是天然埋点，看完 = position ≥ duration − ε，最后观看 = `updated_at`）；manifest 仍是单一事实源。
- **家庭量级**：单写、串行、幂等。

## 4. Epics 与 Stories

### Epic A：R2 用量监控（CLI）
**目标**：随时算出 R2 用量并对阈值告警。
- **Story A1 — `cpv storage`**
  - 作为家长，我想一条命令看到 R2 当前用量与是否超阈值，以便了解成本。
  - **AC**：[ ] `ListObjectsV2` 累加所有对象 size 得总用量；[ ] 按前缀（`videos/` `audiobooks/` 其它）分组；[ ] 与上限（默认 500GB）、低水位（默认 450GB）比较并标记状态（ok/warn/over）；[ ] `--json`。

### Epic B：看完状态查询（Worker）
**目标**：给清理程序提供「哪些视频看完、最后什么时候看的」。
- **Story B1 — Worker `/api/admin/watch-stats`（受保护）**
  - 作为清理程序，我想拿到每个视频的看完状态与最后观看时间，以便判定可删。
  - **AC**：[ ] **受保护**（admin 凭证 / PARENT_PIN 校验，**不是**设备令牌）；[ ] 读 manifest（各视频 duration）+ 聚合 D1 `watch_progress`；[ ] 每个 videoId 返回 `{ watched: bool(任一设备 position ≥ duration−ε), lastWatchedAt }`；[ ] 只回聚合统计，不泄露设备明细。

### Epic C：自动清理（CLI）
**目标**：超阈值时按策略自动删到低水位。
- **Story C1 — `cpv gc`（自动清理已看完旧视频）**
  - 作为家长，我想超 500G 时自动删掉看完很久的旧视频，以便控成本又不误删。
  - **AC**：
    - [ ] 先算用量；**未超低水位则不删**、直接返回。
    - [ ] 候选 = `watched==true` 且 `(now − lastWatchedAt) ≥ 冷却天数(默认 7)` 且 **非收藏/保护**。
    - [ ] 按 **`createdAt` 上传时间 old→new** 排序，依次删除（R2 `videos/<id>/` 全部对象 + manifest 条目）直到用量 ≤ 低水位。
    - [ ] `--dry-run` 只列将删清单 + 预计释放量；默认**全自动执行**（删到水位）；`--json`；进度/日志到 stderr。
    - [ ] 串行、幂等；输出删除日志（删了哪些、释放多少、剩余用量）。
- **Story C2 — 配置与安全护栏**
  - 作为家长，我想能配阈值/水位/冷却天数，且有安全护栏。
  - **AC**：[ ] 配置：`R2_CAP_GB`(默认 500)、`R2_LOW_GB`(默认 450)、`GC_COOLDOWN_DAYS`(默认 7)、admin 凭证（环境变量/参数）；[ ] **收藏/保护视频永不删**；[ ] admin 接口不可达 / 数据不全时**安全失败**（宁可不删）；[ ] 适合 cron/CI 定时跑（退出码/JSON 友好）。

## 5. 数据 / 接口影响 + 待澄清
- **Worker**：新增受保护 `/api/admin/watch-stats`；admin 凭证（建议新增 `ADMIN_TOKEN` secret，或复用 PARENT_PIN）。
- **CLI**：新增 `cpv storage` / `cpv gc`；config 增 admin 凭证 + 阈值。
- **⚠️ 待澄清（收藏保护，关键设计点）**：「我喜欢的」目前是**客户端本地 UserDefaults（每设备）**，**服务端不可见**，所以 CLI 的 gc **无法知道哪些被收藏**。要保护收藏，需引入一处**服务端可见的「保护名单(keep)」**。候选方案（评审时定）：
  1. manifest 给视频加 `keep: true` 字段，`cpv keep <id>` / `cpv unkeep <id>` 维护；
  2. 家长在 App「我的」标记「保留」，上报到 Worker；
  3. gc 读一份本地 `keep.json` 列表。
  **倾向方案 1（manifest `keep` 标记 + cpv 子命令）**，最贴合现有「manifest 单一事实源 + AI 调 CLI」架构。

## 6. 里程碑 / 优先级
- **P0**：Epic A（监控）、Epic B（看完查询）、Epic C（清理）—— 三者构成闭环。
- **P1**：定时任务 / CI 集成（cron 或 GitHub Actions 定时跑 `cpv gc`）。
- **P2**：App「我的」显示容量 + 标记「保留」。

## 7. 测试与验收总览
- **A1**：CLI 算出的用量与 R2 控制台数值一致（合理误差内）。
- **B1**：受保护接口鉴权生效；造一条「看到结尾」的 `watch_progress` → `watched=true`、`lastWatchedAt` 正确。
- **C1**：`--dry-run` 候选正确（看完+冷却+非保护，按上传时间排序）；实跑后用量 ≤ 低水位、被删的确是候选、**收藏/未看完视频安全未动**、manifest 同步。
- **端到端**：模拟超阈值 → `cpv gc` → 用量回落、日志清晰、保护项与未看完视频安全。
